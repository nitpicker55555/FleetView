# The PM card — 2026-11-11

FleetView gets a project manager: one Claude card that is always there, in a column at the right of
the board, that turns a request into a project and a team of other cards, keeps track of them, and
does none of the work itself.

## Why

Supervisor cards had already been run by hand three times (cad-ale-46's Codex SUPERVISOR, SUPERVISOR-QC75,
SUPERVISOR-FIX). Each needed the same scaffolding put together outside FleetView: a role prompt in a
file, a `STATUS_*.md`, and a nudger daemon (fleet-tick, qc75-tick) to wake the supervisor when its
workers moved. The lessons from those runs are written into the PM's role (`PMRole.swift`):

- approve what you can decide; a supervisor that only nudged held the cad-ale-46 work up;
- no rule stricter than the user's own pass line — one such rule kept eighteen qc75 tasks from ever being DONE;
- deliver only what your latest status confirms — a result went out minutes before it was revoked;
- address cards by uuid only — a grep over `pm ls` once removed the supervisor's own card.

Comparable products, looked at before building this: SpaceXAI's Grok Bot (a Chief of Staff /
Projects Manager bot that staffs projects and keeps a Notion board; cloud-only, no project surface)
and DeepSeek's Super-agent prototype (a Router session that only routes, a Worker session per ticket,
events pushed back, an async "full-duplex" loop so the router is never blocked). The PM borrows the
router's rule — never wait in the foreground — and the event push; FleetView already has the project
surface and the roster those two lack.

## What FleetView does for it

A prompt cannot keep itself alive or notice other cards. FleetView does that part (`PMCoordinator`):

- **A fixed home**, `~/.fleetview/pm/`: `CLAUDE.md` (the role; written once, then the user's), `ledger/`
  (the PM's own notes), `roster.json` (which card is the PM, which cards it started), `inbox.jsonl`
  (every status change and digest), `asks/` (side threads), `sessions/` (a copy of each PM
  transcript, appended on every Stop — Claude's own copies are not safe: a 30-day cleanup removed
  ~3,600 on 2026-10-06).
- **A card with no window.** Made at launch if there is none, in the PM project (the home folder),
  started like a hidden terminal (`AppState.startWithoutWindow`): resuming its last conversation, or
  `claude --dangerously-skip-permissions` the first time — bypass, like the rest of the fleet, which
  was the user's call. The board, the sidebar and the web board leave the PM and its folder out;
  the web pins the PM above everything. A closed PM is brought back by the 30 s tick.
- **Its workers.** A `/new` whose caller (X-FV-Caller, from `project-manager`) is the PM's card is
  recorded as the PM's. `enterStatus` reports their transitions: a finished turn, a needs-you, an exit or
  a close. They are batched and typed into the PM as one `[FleetView 收件箱]` message — only while the PM
  is idle (never into its turn, never into a bare shell), at most every 45 s.
- **Side questions**, one thread per project (and `general`). The first question forks the PM's
  conversation (`claude -p --resume <pm> --fork-session`); every follow-up resumes that fork, so the
  thread keeps its context and the main line is never touched. Read-only: `--permission-mode dontAsk`
  with an allowlist of reading tools and `project-manager`'s read-only commands — a write is refused,
  not asked about (checked against Claude Code 2.1.319). Each thread is kept as
  `asks/<project>.md`, and the next digest names threads with new turns, which is how the main line
  learns of them.

## Where you see it

- **Desktop:** a 400 pt column under the top bar, right of the board (`PMDock`), toggled from the bar.
  It is the web dashboard in dock mode (`/?dock=pm`) in a WKWebView — the conversation view, images,
  send status and terminal mirror already exist there, and the phone needs them anyway, so the
  side-question UI is written once. It steps aside for the session tree and the triggers panel, and
  in a window too narrow to keep a usable board beside it.
- **Web:** the PM pinned above the board; on its card the bar has a dropdown — the main line, or a
  project's side thread. In a side thread the composer asks it.
- **CLI:** `project-manager pm` (status) · `pm say <text> [-w]` · `pm show` · `pm ask <project> <q>` ·
  `pm thread <project>` · `pm threads` · `pm refork <project>` · `pm start`. All HTTP (`/manager…`),
  so `-u` reaches another Mac's PM. No auth, like the rest of the API: anyone on the LAN/tailnet can
  talk to the PM and read its side threads.

On a headless FleetView the PM is off unless `FV_PM=1` — the Mac mini is shared, and a manager nobody
looks at spends tokens on digests.

## How it was checked

- The ask path against the real CLI: a fork returns a new session id, a follow-up resumed by that id
  remembers the first answer and keeps the id, `project-manager ls` runs, a Write is denied; the exact
  `zsh -lc` line with its quoting returns parseable JSON.
- The page, extracted and driven in headless Chrome against a stub of `/state`, `/conversation` and
  `/manager…` (dock mode at 400×860, board at 390×844): 29 checks — dock shows only the PM, dropdown
  items and light dismiss, a side thread's send goes to `/manager/ask` and never to `/type`, a
  follow-up lands in the same fork, the digest renders as a notice, the PM is pinned and its folder is
  not a project, workers wear the badge.
- `project-manager pm …` against the same stub, `-u` included.
- `FleetView --snapshot`: the column under the top bar, the bar keeping its full width.

## Not done yet

- A typed report from workers (`project-manager report ready|blocked|failed`) — today "idle" is read as
  "finished a turn", which is not the same as finished.
- A signal when the user types into a worker directly, so the PM leaves it alone.
- A hook that refuses foreground waits in the PM's own session; the role asks for it, nothing enforces it.
