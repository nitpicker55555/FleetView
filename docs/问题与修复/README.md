# 问题与修复

FleetView 在实际使用中出过的问题，每个问题一份记录：现象、怎么查到的、根因、修了什么、怎么验证、还有什么没覆盖。

和 `docs/design/` 的分工：`design/` 放实现之前写的设计文档；这里放出了事之后的记录。一次事故如果引出了较大的设计改动，设计文档仍放 `design/`，两边互相链接。

## 命名约定

```
YYYY-MM-DD-<问题简述>.md
```

日期是发现问题的日期。文档写完不删、不覆盖；同一问题又出现时，在原文档末尾追加一节，标明日期。

## 文档头

每份文档开头放一个元信息表：

| 字段 | 说明 |
|---|---|
| 发现日期 | `YYYY-MM-DD` |
| 状态 | 排查中 / 已修复（未部署）/ 已修复 / 已知未修 |
| 影响 | 一句话：谁、损失了什么 |
| 对应代码版本 | 写作时的 git commit |
| 修复 | 修改了哪些文件；有 commit 就写 commit |

| 2026-10-30 | [复制出来的卡片，网页 chat 是空的](2026-10-30-forked-card-empty-chat.md) | 已修复 | `--fork-session` 一启动就报告新 session 的文件，但文件要等第一条消息才写出来；`transcriptPath` 把"文件还不存在"一律当成没有对话。修复：复制时记下原对话（`forkedFrom`），fork 还没有自己的文件时 chat 显示原对话 |
| 2026-10-30 | [网页端断线后不刷新就连不回来](2026-10-30-web-stays-offline-until-reload.md) | 已修复 | 轮询请求都没有超时。断网时发出的请求卡在死连接上，几秒内占满浏览器对同一主机的 6 个连接，之后所有请求（包括判断离线的 ping）都在排队，网络恢复了也不会连回来，只有刷新能把它们丢掉。修复：请求加超时、可以一次全部丢弃；轮询不和自己重叠；网络恢复时自动重连，点网络按钮手动重连（终端页一起重载） |
| 2026-10-30 | [关掉的终端窗口留下僵尸进程](2026-10-30-closed-windows-leave-zombies.md) | 已修复 | 生产实例名下累积了 42 个 `<defunct>`，每关一个窗口多一个。SwiftTerm 的 `terminate()` 在子进程退出前就取消了自己的退出监听，而 `waitpid` 只在那个监听里调用。修复：关窗口时由 FleetView 轮询 `waitpid` 回收；用退出事件监听在测试里 30 次都没触发 |
| 2026-10-26 | [网页 chat 停在上下文压缩那一刻](2026-10-26-web-chat-frozen-at-compaction.md) | 已修复 | 一张 Claude 卡片的网页 chat 停在 07:46，终端已到 08:52。挑当前分支时，压缩原样保留、留在旧链上的最后一条记录被当成了分支末端；它往回走能遇到卡片的提示，而真正的末端往回走只能遇到后台通知和压缩摘要。修复：压缩带走的记录不算末端；找提示时跳过注入的 user 记录 |
| 2026-10-22 | [关掉卡片后 agent 进程还在](2026-10-22-agent-outlives-closed-card.md) | 已修复 | 关卡片只做 `tmux kill-session`，靠 SIGHUP 让 agent 退出。一个 sp-claude 下的 Claude 收到挂断后没有退出，在主线程空转了 46 小时，同时一直占着 sub-pool 租约；卡片上显示 closed，点开后同一会话又起了第二个进程。修复：kill 之前记下 pane 里的进程，kill 之后检查，还活着的按 SIGTERM → SIGKILL 处理（`ProcessReaper`） |
